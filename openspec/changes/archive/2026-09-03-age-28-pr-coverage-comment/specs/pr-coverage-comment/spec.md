## ADDED Requirements

### Requirement: A dedicated pull-request job publishes the coverage comment
`.github/workflows/pull-request.yml` SHALL define a job that publishes the unit-test coverage summary as a comment on the pull request. The job SHALL depend on the job that runs the tests, and SHALL consume the `coverage-report` artifact defined by the `unit-test-coverage` capability rather than running the test suite itself.

The job SHALL live in `pull-request.yml` rather than in the reusable `tests.yml` workflow, so that `tests.yml` remains free of pull-request-specific logic and can continue to be called unchanged by `production.yml`.

The job SHALL NOT be folded into the existing preview-deploy comment job, because that job is gated on a deployment having occurred and would therefore skip the coverage comment on pull requests that deploy nothing.

The job SHALL check out the repository (needed for the Vitest config file and for git history) but SHALL NOT install dependencies, since the reporting action is self-contained and does not require the workspace's `node_modules`.

#### Scenario: Coverage comment appears on a pull request
- **WHEN** a pull request against `main` runs the PR workflow and the unit-test job completes
- **THEN** a comment is posted on the pull request containing the unit-test coverage summary

#### Scenario: The comment is posted for a non-deploying pull request
- **WHEN** a pull request changes only files that trigger no preview deployment, so the deploy matrix is empty and the preview-comment job is skipped
- **THEN** the coverage comment is still posted

#### Scenario: Production runs post no comment
- **WHEN** a push to `main` runs `production.yml`, which calls the same `tests.yml` reusable workflow
- **THEN** no coverage comment job runs, because the job is defined only in `pull-request.yml`

#### Scenario: The comment job does not re-run the test suite
- **WHEN** the coverage comment job runs
- **THEN** it obtains coverage data by downloading the `coverage-report` artifact, and does not execute `yarn test:coverage`

### Requirement: The comment is generated by `davelosert/vitest-coverage-report-action`
The coverage comment SHALL be produced by the `davelosert/vitest-coverage-report-action` GitHub Action, pinned to a major version tag consistent with how the repository pins its other actions.

The action SHALL be configured with:
- `file-coverage-mode: changes`, so the per-file table lists only files touched by the pull request
- `vite-config-path` pointing at the root `vitest.config.ts`, so the action reads `coverage.thresholds` from the single place the floor is defined and renders each metric against it

The action's coverage-file path inputs SHALL be left at their defaults, and the artifact SHALL be downloaded into `coverage/` at the workspace root so those defaults resolve.

The action SHALL NOT be configured with a base-branch comparison. The comment reports current coverage against the configured threshold, not a delta against `main`.

The action SHALL manage its own comment: it posts one comment per pull request and updates that comment on subsequent runs rather than appending a new one. The existing preview-deployment comment SHALL remain a separate comment and SHALL NOT be merged with the coverage comment.

#### Scenario: The comment reports metrics against the configured threshold
- **WHEN** the coverage comment job runs and the root `vitest.config.ts` declares `lines` and `statements` thresholds
- **THEN** the comment shows the lines and statements figures marked against those thresholds, without the threshold value being duplicated in the workflow file

#### Scenario: The per-file table is limited to changed files
- **WHEN** a pull request modifies two source files out of the many matched by `coverage.include`
- **THEN** the comment's per-file table lists those two files and does not list every measured file in the repository

#### Scenario: Re-running updates the existing comment
- **WHEN** a second commit is pushed to a pull request that already has a coverage comment
- **THEN** the existing coverage comment is updated in place, and a second coverage comment is not created

#### Scenario: The preview-deploy comment is unaffected
- **WHEN** a pull request produces both a preview deployment and a coverage comment
- **THEN** the preview-deployment comment and the coverage comment exist as two separate comments, each managed by its own job

### Requirement: The comment job holds write permission in isolation
The coverage comment job SHALL declare `permissions: pull-requests: write`. That permission SHALL be scoped to this job only and SHALL NOT be granted to the job that runs the test suite, so the elevated token is held by a job that does nothing but read a downloaded artifact and post a comment.

#### Scenario: Only the comment job can write to the pull request
- **WHEN** the PR workflow runs
- **THEN** the coverage comment job declares `pull-requests: write`
- **AND** the job calling the `tests.yml` reusable workflow does not

### Requirement: The comment is posted even when the coverage gate fails
The coverage comment job SHALL be conditioned on `always()`, so that it runs after a test job that failed. A run that falls below the coverage threshold is the case where the per-file breakdown is most useful, and suppressing the comment there would remove the explanation of the failure.

Posting the comment SHALL NOT mask the failure: the test job's own failed status remains the enforcing signal, and the comment job SHALL NOT set the test job's result.

If the coverage artifact is absent — for example because the suite crashed before any reporter was written — the job SHALL fail rather than post an empty or misleading comment.

#### Scenario: Coverage below the threshold still produces a comment
- **WHEN** `yarn test:coverage` fails because line coverage fell below the configured floor
- **THEN** the test job is red
- **AND** the coverage comment is still posted, showing the failing metric and the changed files' figures

#### Scenario: A failing gate is still reported as a failure
- **WHEN** the coverage gate fails and the coverage comment is posted successfully
- **THEN** the pull request's overall check status is still failing

#### Scenario: A missing artifact fails the job
- **WHEN** the test suite crashes before writing coverage reporters, so no `coverage-report` artifact exists
- **THEN** the coverage comment job fails, and no comment claiming zero or empty coverage is posted

### Requirement: Fork pull requests do not fail the comment job
The coverage comment job SHALL be guarded so that it does not run for pull requests originating from a fork, whose `GITHUB_TOKEN` is read-only and cannot post a comment. Without the guard, every fork pull request would show a permanent failure from a job that cannot succeed.

The workflow SHALL NOT use the `pull_request_target` event to work around this, because that event grants a write-scoped token to code originating from the fork.

#### Scenario: A fork pull request skips the comment job
- **WHEN** a pull request is opened from a fork of the repository
- **THEN** the coverage comment job is skipped rather than failing

#### Scenario: A same-repository pull request runs the comment job
- **WHEN** a pull request is opened from a branch in the repository itself
- **THEN** the coverage comment job runs and posts the comment

#### Scenario: The workflow trigger is not escalated
- **WHEN** the PR workflow definition is inspected
- **THEN** it is triggered by `pull_request` and not by `pull_request_target`
